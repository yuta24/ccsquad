# ハーネス設計ガイド

## ハーネスが解決する問題

LLM エージェントの長時間タスクには2つの構造的な障害がある:

1. **コンテキスト劣化** — ウィンドウが埋まるにつれ一貫性が失われ、制限に近づくと作業を打ち切る傾向がある
2. **自己評価バイアス** — 自分が生成した成果物を評価させると、品質が平凡でも肯定的に評価してしまう

ハーネスはこれらに構造的に対処する仕組みである。

## 設計原則

### 1. Generator-Evaluator 分離

実装と評価は別コンテキストで行う。自己評価バイアスを排除する。

- `execute` フェーズ (developer エージェント) = Generator
- `review` フェーズ (人間 or reviewer エージェント) = Evaluator
- review はデフォルトで一時停止し、生成者とは別のコンテキストで評価する
- `auto` キーワードを付けると reviewer エージェントによる自動レビューが可能（一時停止しない）

### 2. コンテキストリセット

圧縮（要約）ではなくリセット（完全クリア）+ 構造化ハンドオフで品質を維持する。

- フェーズ遷移のたびにコンテキストがリセットされる前提で設計する
- ハンドオフ情報はジョブ body に永続化:
  - `## Acceptance Criteria` — 何を達成すべきか
  - `## フェーズログ` — 何が起きたか
- 次フェーズのエージェントは body を読むだけで作業を継続できる状態にする

### 3. スプリント契約

execute に入る前に「何をもって完了とするか」を合意する。曖昧なまま実装に入るとループが収束しない。

- plan フェーズで Acceptance Criteria を具体的チェックリストとして定義する
- review では各項目を検証し、reject 時はどの基準が未達か明記する

### 4. 反復による品質収束

1回で完璧を求めず、reject → rework ループで段階的に品質を高める。

- review の rejected 遷移先を execute（または plan）に設定する
- `--max-iterations` で無限ループを防止（デフォルト: 10）
- reject メッセージが次の反復の指針になる

### 5. モデル進化に伴う再評価

ハーネスの各コンポーネントは「モデルにできないこと」の仮定をエンコードしている。

- パフォーマンスに寄与していないフェーズは削除を検討する
- シンプルに始めて、必要な場合のみ複雑さを追加する

## ワークフロー選択の指針

| タスクの特性 | 推奨パターン |
|---|---|
| スコープが明確、小〜中規模 | 基本: plan → execute → review |
| 未知の技術・ドメインを含む | 調査分離: research → design → execute → review |
| 品質要求が高い | 二段階レビュー: plan → execute → review → verify |

迷ったら基本パターンから始め、必要に応じてフェーズを追加する。
具体的な CLI テンプレートは `job` スキルを参照。
