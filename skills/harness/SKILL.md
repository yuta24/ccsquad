# ハーネス設計ガイド

## ハーネスが解決する問題

LLM エージェントの長時間タスクには2つの構造的な障害がある:

1. **コンテキスト劣化** — ウィンドウが埋まるにつれ一貫性が失われ、制限に近づくと作業を打ち切る傾向がある
2. **自己評価バイアス** — 自分が生成した成果物を評価させると、品質が平凡でも肯定的に評価してしまう

ハーネスはこれらに構造的に対処する仕組みである。

## 設計原則

### 1. Generator-Evaluator 分離

実装と評価は別コンテキストで行う。自己評価バイアスを排除する。

- `execute` フェーズ (developer エージェント) = Generator
- `review` フェーズ (人間 or reviewer エージェント) = Evaluator
- review はデフォルトで一時停止し、生成者とは別のコンテキストで評価する
- `auto` キーワードを付けると reviewer エージェントによる自動レビューが可能（一時停止しない）

### 2. コンテキストリセット

圧縮（要約）ではなくリセット（完全クリア）+ 構造化ハンドオフで品質を維持する。

- フェーズ遷移のたびにコンテキストがリセットされる前提で設計する
- ハンドオフ情報はジョブファイルに永続化:
  - `acceptance_criteria` (frontmatter) — 何を達成すべきか
  - `## フェーズログ` (body) — 何が起きたか
- 次フェーズのエージェントは frontmatter と body を読むだけで作業を継続できる状態にする

### 3. スプリント契約

execute に入る前に「何をもって完了とするか」を合意する。曖昧なまま実装に入るとループが収束しない。

- plan フェーズで Acceptance Criteria を具体的チェックリストとして定義する
- review では各項目を検証し、reject 時はどの基準が未達か明記する

### 4. 反復による品質収束

1回で完璧を求めず、reject → rework ループで段階的に品質を高める。

- review の rejected 遷移先を execute（または plan）に設定する
- `--max-iterations` で無限ループを防止（デフォルト: 10）
- reject メッセージが次の反復の指針になる

### 5. モデル進化に伴う再評価

ハーネスの各コンポーネントは「モデルにできないこと」の仮定をエンコードしている。

- パフォーマンスに寄与していないフェーズは削除を検討する
- シンプルに始めて、必要な場合のみ複雑さを追加する

## ワークフロー選択の指針

| タスクの特性 | 推奨パターン |
|---|---|
| スコープが明確、小〜中規模 | 基本: plan → execute → review |
| 未知の技術・ドメインを含む | 調査分離: research → design → execute → review |
| 品質要求が高い | 二段階レビュー: plan → execute → review → verify |
| 大規模 or 複数の設計選択肢がある | 並列探索: explore → design → execute → review |

迷ったら基本パターンから始め、必要に応じてフェーズを追加する。
具体的な CLI テンプレートは `job` スキルを参照。

### 並列探索パターン

feature-dev プラグインの設計に着想を得た、**多角的な事前調査**のパターン。
複数エージェントが異なる視点でコードベースを並列調査し、その結果を統合してから設計・実装に進む。

#### いつ使うか

- 変更対象が広範で、既存パターンの把握が重要なとき
- 設計の選択肢が複数あり、判断材料を集めたいとき
- 既存コードベースの慣習に厳密に従う必要があるとき

#### 仕組み

```
explore (並列 plan)  →  design (plan)  →  code (execute)  →  review
  ├─ agent A: 類似機能・再利用可能なコードを調査
  ├─ agent B: アーキテクチャ層・抽象化パターンを調査
  └─ agent C: テスト慣習・統合ポイントを調査
```

1. **explore フェーズ**: `agents:` で 2〜3 エージェントを並列起動し、それぞれ異なる constraint で調査する。各エージェントの調査結果はフェーズログに統合される
2. **design フェーズ**: explore の結果を踏まえて単一の設計方針を決定する。Acceptance Criteria を具体化する
3. **code / review**: 通常の execute → review ループ

#### constraint の設計原則

並列探索の価値は **視点の分離** にある。constraint は以下のように設計する:

- **重複を避ける**: 各エージェントが異なる側面を調査するよう明確に分割する
- **具体的にする**: 「コードを調べる」ではなく「認証ミドルウェアの実装パターンと依存関係を特定する」
- **成果物を指定する**: 何をフェーズログに残すべきか明記する

よく使う視点の分割例:

| 分割軸 | constraint 例 |
|---|---|
| 機能 / 構造 / テスト | 類似機能の実装 / アーキテクチャ層 / テストパターン |
| フロントエンド / バックエンド / インフラ | UI コンポーネント / API 層 / DB スキーマ |
| 現状把握 / 課題分析 / 外部事例 | 既存実装の調査 / 技術的負債の特定 / OSS での解決例 |

#### 調査分離パターンとの使い分け

| | 調査分離 | 並列探索 |
|---|---|---|
| 調査の深さ | 1 エージェントが順次調査 | 複数エージェントが並列で多角的に調査 |
| 適するケース | 未知のドメインを段階的に理解 | 既知だが広範な領域を効率的にカバー |
| コスト | 低（1 エージェント分） | 高（N エージェント分） |
